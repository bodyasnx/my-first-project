# AI-NOTES: нотатки про роботу з AI-асистентом

## Інструмент і спосіб роботи

- **Інструмент:** GitHub Copilot Chat у VS Code (безкоштовний план), режим Agent, вибір моделі Auto. У відповідях чат показував модель (GPT-6 Luna) і витрату кредитів (близько `0.1 credits` за коротку відповідь).
- **Проєкт:** статичний лендінг VXE R1 Pro Max (корінь репозиторію: `index.html`, `style.css`, `script.js`). Теку `portfolio-react` у запитах я явно виключав.
- **Як я працював:** потрібні файли додавав у контекст чату через `+` → Files. Режиму Ask у моїй версії VS Code не було, тож у кожен запит дописував «НЕ редагуй файли». Так я спершу читав запропонований код і вносив його вручну, а не приймав кнопкою Apply.
- **Перший запуск:** перший запит я надіслав до входу в акаунт, і чат показав вікно авторизації. Після входу через GitHub (кнопка Continue with GitHub) запит довелося надіслати ще раз.
- **Перевірка:** кожну зміну я тестував у браузері (повідомлення на сторінці, консоль, вкладка Network) і комітив окремо.

## Промпти, що спрацювали

### 1. Додати поле «Телефон» з валідацією

**Промпт:**

```
Контекст: це статичний лендінг у корені проєкту (index.html, style.css, script.js; НЕ чіпай теку portfolio-react). У script.js є обробник submit форми .contact-form: він перевіряє ім'я, email, повідомлення й згоду, потім надсилає дані через fetch POST. Помилки показує функція showMessage(текст, 'error').

Завдання: додай у форму необов'язкове поле «Телефон» (input type="tel", id="phone", name="phone") і валідацію.
Правило: якщо поле не порожнє, воно має відповідати формату +380XXXXXXXXX (плюс, 380 і ще 9 цифр), інакше показати помилку через showMessage. Значення телефону додай в об'єкт data, що надсилається.

Обмеження: не змінюй інші поля й стилі, не додавай бібліотек, використай існуючий клас form-field, коментарі пиши українською.
Формат відповіді: покажи лише змінені фрагменти й вкажи, у якому файлі та після якого рядка вставити.
Важливо: НЕ редагуй файли й не запускай команд. Лише покажи змінені фрагменти кодом у відповіді.
```

**Відповідь асистента:** чотири фрагменти: HTML нового поля в блоці `form-field`, читання значення в `script.js`, перевірка регулярним виразом `/^\+380\d{9}$/` у ланцюжку `else if` і додавання `phone` в об'єкт `data`.

**Чому промпт спрацював:** він містив контекст (що за проєкт і який обробник), чітку ціль, точне правило формату, обмеження (нічого зайвого не чіпати) і формат відповіді (лише змінені фрагменти з місцем вставки). Асистент не переписував чужий код і вказав, куди що вставити.

**Результати тестів:**

| Введення в полі «Телефон» | Результат |
|---|---|
| порожньо | форма відправлена; у Network → Payload `phone: ""` |
| `45645645646` (без плюса) | помилка «Введіть телефон у форматі +380XXXXXXXXX.» |
| `+380501234567` | успіх; у Network → Payload `phone: "+380501234567"` |

### 2. Уточнення: стилі нового поля

**Проблема:** після вставки поле «Телефон» виглядало інакше за «Ім'я» й Email (біле, з тонкою рамкою).

**Промпт:**

```
Поле «Телефон» (input type="tel", id="phone") виглядає інакше за поля «Ім'я» та Email: біле, з тонкою рамкою. У style.css стилі полів задані селектором для input[type="text"], input[type="email"], select, textarea.
Завдання: зроби так, щоб input[type="tel"] виглядав так само, як інші поля, змінивши лише існуючі селектори в style.css (без нових правил і без зміни index.html).
Формат відповіді: покажи лише змінені селектори. НЕ редагуй файли.
```

**Відповідь:** до списку селекторів додано `input[type="tel"]`. Я перевірив пошуком `Ctrl+F`, що `input[type="email"]` зустрічається у `style.css` лише в одному місці, тож відповідь була повною. Після `npm run build:css` поле стало виглядати як решта.

**Чому спрацювало:** у запиті описано видиму проблему, названо файл і поточний селектор, а також вказано, що саме можна змінювати.

### 3. Пояснення регулярного виразу

**Промпт:**

```
Поясни детально цей рядок з script.js і кожен символ регулярного виразу:
} else if (phone !== '' && !/^\+380\d{9}$/.test(phone)) {
Що означають ^, \+, \d, {9}, $ і метод test()?
Формат відповіді: короткий список символів із поясненням. НЕ редагуй файли.
```

**Відповідь:** список символів: `^` початок, `\+` буквальний плюс (зворотна риска потрібна, бо `+` має спеціальне значення), `380` літерали, `\d` цифра, `{9}` рівно 9 повторів, `$` кінець, `.test()` повертає `true` або `false`; підсумок про умову правильний.

**Звірка з документацією MDN** (розділ про регулярні вирази та `RegExp.prototype.test()`): пояснення збіглося. Дрібна неточність: асистент називає `^` «початком рядка», а в MDN це початок усього введення (початок кожного рядка тексту лише з прапорцем `m`, якого тут немає).

### 4. Діагностика помилки (навмисно зламаний код)

**Що я зробив:** у `script.js` змінив селектор `'#phone'` на `'#phon'` (такого елемента немає). Після натискання «Надіслати» відправка не відбулась, а в консолі з'явилась помилка:

```
Uncaught (in promise) TypeError: Cannot read properties of null (reading 'value')   script.js:98
```

**Промпт:**

```
Після мого останнього редагування форма перестала відправлятися. У консолі браузера:
Uncaught (in promise) TypeError: Cannot read properties of null (reading 'value') — script.js:98
Поясни, що означає ця помилка, у якому рядку script.js причина і чому значення дорівнює null. Запропонуй виправлення. НЕ редагуй файли.
```

(Файл `script.js` був у контексті чату, код у запит я не вставляв.)

**Відповідь асистента:** пояснив, що `document.querySelector()` повертає `null`, коли елемент із таким селектором не знайдено, а доступ до `.value` у `null` дає цю помилку. Причину вказав точно: у рядку 98 селектор `'#phon'` не збігається з `id="phone"`. Запропонував замінити на `'#phone'`. Також пояснив, що `Uncaught (in promise)` з'являється, бо помилка виникає всередині асинхронного обробника й не перехоплюється.

**Моя оцінка:** діагностика влучна: знайдено правильний рядок, механізм помилки пояснено правильно, виправлення мінімальне. Асистент не додав зайвих порад (наприклад, перевірок на `null`, які замаскували б справжню причину). Після перевірки я повернув код командою `git restore script.js`.

### 5. Рефакторинг: винести валідацію в окрему функцію

**Промпт:**

```
Зроби рефакторинг блоку валідації в обробнику submit форми .contact-form у script.js: винеси перевірки (ім'я, email, телефон, повідомлення, згода) в окрему функцію validateForm({ name, email, phone, message, consent }), яка повертає текст помилки або порожній рядок. Поведінка й тексти помилок мають лишитись точно такими самими, порядок перевірок не змінюй. Не змінюй fetch, showMessage, стан кнопки й інші частини.
Формат відповіді: покажи нову функцію validateForm і те, як змінити обробник; поясни, що саме спростилось. НЕ редагуй файли.
```

**Відповідь асистента:** нова функція `validateForm({ name, email, phone, message, consent })` з тим самим ланцюжком перевірок, що повертає текст помилки або `''`, і короткий блок в обробнику: `const error = validateForm(...)`, далі `if (error !== '') { showMessage(error, 'error'); return; }`.

**Моя критична перевірка перед застосуванням:** порядок перевірок збережено (ім'я → email → телефон → повідомлення → згода); тексти помилок дослівно ті самі; логіка телефону не змінилась (поле необов'язкове, формат `+380` і 9 цифр); `fetch`, `showMessage`, стан кнопки та `finally` не торкнуто. Дрібне зауваження до стилю: у функції лишились `else if` після `return`, хоча `else` там зайве (на поведінку не впливає).

**Як я перевірив, що поведінка не змінилась (ті самі тести після рефакторингу):**

| Дія | Результат |
|---|---|
| порожнє ім'я | «Введіть ім'я.» ✓ |
| email без `@` | «Введіть коректний email: він має містити «@».» ✓ |
| `45645645646` у телефоні | «Введіть телефон у форматі +380XXXXXXXXX.» ✓ |
| порожнє повідомлення | «Напишіть повідомлення.» ✓ |
| без галочки згоди | «Потрібна згода на обробку даних.» ✓ |
| усе правильно, `+380501234567` | успіх; у Payload `phone: "+380501234567"` ✓ |
| усе правильно, телефон порожній | успіх; у Payload `phone: ""` ✓ |

Результат закомічено: `Виніс валідацію форми в функцію validateForm`.

## Випадки, коли AI потребував уточнення або виявився неповним

1. **Поле без стилів.** Асистент точно виконав обмеження «не змінюй стилі» і додав лише HTML та JavaScript. Але в `style.css` оформлення полів було прив'язане до `type="text"` та `type="email"`, тож поле `type="tel"` вийшло неоформленим. Асистент про це не попередив. Довелось робити другий запит (промпт №2). Висновок: правильна відповідь на запит може бути неповною щодо всього завдання, і про наслідки обмежень доводиться думати самому.
2. **Неточність у поясненні.** `^` названо «початком рядка» замість «початку введення». Помилка дрібна, але виявлена лише завдяки звірці з MDN.
3. **Двозначна інструкція щодо заміни коду.** У відповіді з рефакторингом було написано «замініть блок від `let error = '';` до перевірки `if (error !== '')` включно». Було неясно, чи входить у блок закриваюча дужка цього `if`, тож я перепитав, які саме рядки видаляти. Висновок: інструкції асистента про те, що саме замінювати, варто перечитувати двічі й перевіряти за номерами рядків, бо легко залишити зайву `}` або продублювати код.
4. **Різні повідомлення про email.** Під час перевірки я побачив два різні тексти для email без `@`: коротку підказку під час вводу «Email має містити «@».» (з практичної 15, подія `input`) і довше повідомлення «Введіть коректний email: він має містити «@».» після натискання «Надіслати» (з `validateForm`). Щоб перевіряти саме функцію, потрібно натискати «Надіслати», а не дивитись на підказку.

## Моя власна помилка, яку виявило тестування

Я застосував три з чотирьох запропонованих змін і пропустив рядок `const data = { name, email, phone, message };`. Повідомлення на сторінці працювали (валідація відпрацьовувала), і лише вкладка Network → Payload показала, що `phone` не передається на сервер. Виправив окремим комітом `Виправив: передав телефон у даних запиту`. Висновок: перевіряти треба не лише видимий результат на сторінці, а й те, що реально відправляється.

## Правила, які я виводжу для себе

1. У запиті завжди вказувати **контекст, ціль, обмеження й формат відповіді**.
2. Просити асистента не редагувати файли, поки я не прочитав код; зміни вносити самому й розуміти кожен рядок.
3. Передавати код через **файли в контексті**, а не вставляти фрагменти зі спецсимволами в текст запиту: зворотні риски й подібне можуть спотворитись.
4. Перевіряти **повноту** відповіді: чи покрито всі місця, де зміна потрібна (пошук по проєкту), і чи не зламали обмеження в запиті щось суміжне (наприклад, «не міняй стилі» залишило поле без оформлення).
5. Застосовувати **всі** запропоновані зміни (скласти список і відмічати), а потім перевіряти за допомогою тестів.
6. Тестувати і коректні, і некоректні дані, а також дивитись **Network → Payload**, а не лише повідомлення на сторінці.
7. Для діагностики помилки давати асистентові **точний текст із консолі й номер рядка**; відповідь звіряти з реальним кодом.
8. Перед рефакторингом вимагати збереження поведінки й після нього повторювати **ті самі тести**.
9. Звіряти пояснення асистента з офіційною документацією (MDN).
10. Не вставляти в чат паролі, токени й особисті дані.
11. Кожну завершену зміну комітити окремо з осмисленим повідомленням, а перед експериментом із поломкою кодом переконатись, що попередня робота закомічена (інакше `git restore` її забере).

## Висновок

AI-асистент добре виконує чітко сформульовані невеликі задачі (додати поле, пояснити регулярний вираз, знайти причину помилки за текстом із консолі, зробити рефакторинг із збереженням поведінки). Але він виконує запит **буквально**: якщо в запиті обмеження чи прогалина, результат буде неповним, і заповнити їх мусить людина. Тому відповідальність за перевірку (читання коду, тести, Network, документація) лишається на мені.
